# Working on Baselane mods

Claude Code mods: plugins of function hooks (Claude Code 2.1.288, early-access API).

## Layout

- `engines/<engine>/engine.json`: the engine's shared files and how a mod wires its rules (see `scripts/build.mjs`).
- `engines/<engine>/hooks/engine.ts`: the engine. `hooks/rules/<id>.ts`: one rule per file.
- `engines/<engine>/tests/`: shared test helpers and one `<id>.test.ts` per rule.
- `catalog/<name>.json`: `{ "engine", "mods": [{ "name", "description", "rules": [ids] }] }`. A mod with several rules is a pack.
- `plugins/`: GENERATED by `node scripts/build.mjs`. Never edit it by hand.
- `engines/<engine>/hooks/hosts/<name>.ts`: a host, one hook registration with the `$` closures it hands the rules (see below).
- `engine.json` keys: `tests`, `ruleExport` (`rule` or `create`), and optional `register`, `needs`, `hosts`, `shared`, `types`, `options`, `userConfig`, `nameToken`, `stateOwner`. The header of `scripts/build.mjs` says what each one does. Only the plugin that owns a `$.state` value may write it, and the owner is the mod's name, so an engine whose mods share one source uses `nameToken` (replaced in every copied file) or `stateOwner` (replaced in listed files, and the build fails if a listed file never names it). The band engine uses the first, the command engine the second.

## A mod ships only the code its rules import

`claude plugin validate` lists every hook and `$` call in the import closure of a mod's `hooks/register.ts`, and the public gallery shows that list as what the mod can do. So the list must be what the mod's own rules use, and nothing more.

- The build copies only the files `register.ts` imports, directly or through other files. A file no rule imports does not ship. A shared test ships only when the hooks files it imports ship.
- Put each `$` capability in its own module: a host in `hooks/hosts/`. A `$` call cannot cross an import (the module fails to load), so the host holds the hook literal and builds the closures there; the engine keeps the `$`-free body and takes the closures. A host that does not give a tool hands a stub that rejects with "not given to this mod".
- `engine.json` `needs` names what each rule uses beyond the engine core (a capability such as `run`, or a hook such as `after`); `hosts` lists, per group, the hosts and what each `gives`. The build picks the smallest host that covers the mod's needs and writes the call into `register.ts`. A group that no rule needs gets the host with empty `gives` (see the `scripts/build.mjs` header). The build stops if a rule needs something that no host gives, or if `needs` names a rule that does not exist.
- The engine's own `register` holds only the hooks and calls every mod of the engine uses.
- `on` may only be passed to a function declared at the top level of the same file or imported from the mod's own files, and that function may not return a value (`const x = f(on)` fails to load). State that the engine's hooks and its hosts share comes from `shared` instead.
- When a rule starts to use a new tool, add it to `needs`; if no host gives that set, add a host. A missing need makes the rule's own tests fail (the stub rejects).
- A mod that really runs a program, writes a file, reaches the network, fills the prompt or calls a model says so in its catalog description, in plain words ("read with git", "runs your formatter").
- Run `node scripts/calls-report.mjs` after a change: one line per mod with its hooks and calls. No mod may gain a call it does not use.

## Check before you report

`bash scripts/check.sh` rebuilds, then runs `claude plugin validate`, `claude plugin test` and a type check on every mod and engine. Pass mod names to check only those. A change is done only when it prints `check: 0 failure(s)`.

Prove each test can fail: break a copy of the rule in a scratch folder and confirm a test fails.

## API facts that are not obvious

The types file is the authority. Its path is in `scripts/check.sh` (`TYPES`). Grep it for the event or noun at hand.

- A hook is `($, e, next)`. `next(e)` continues; returning without `next` answers for the rest.
- Never pass `$` as an argument, store it or return it: the module then fails to load. Call `$.noun.method()` at the call site, or pass closures that do. The one exception: a function declared in the same file may take `$` (validate lists its calls "via" that function); never one that is imported.
- A hook is a function literal or the name of one: `on(event, wrap(fn))` does not load.
- `tool.call` answers only `{ deny }` or `{ result }`. To ask the person, use `classic.PreToolUse` returning `{ ask }`. Its `e` is `{ tool, tool_use_id, ...args }`.
- `$.process.run(argv, init)`: argv array first. Output caps at 4 MiB (`isStdoutTruncated`); a timeout rejects.
- `$.session.cwd()`, `$.session.usage()` (`context.percent`, `cost`), `$.ui.toast(text)`, `$.ui.status(text)`, `$.ui.log(text)`.
- Panes: `$.ui.open({ id, title })` plus a `ui.render` hook on `{ component: 'Pane', requestId: id }`. Elements come from `$.ui.resolve(e)` (no element globals). State a drawing reads lives in `$.state` (declare it in the mod's `types/index.d.ts` under `interface PluginState`), not module variables. A render hook never writes state.
- Slash commands: `$.command.register({ name, description })` in `session.start`, answered by `on('command.run', { command: name }, ...)` returning `{ text }`.
- In `claude plugin test`: the test's own `on` hooks sit beneath the plugin and stand for the engine. A hook for a `$` call returns `{ value: X }` (for example `on('session.cwd', () => ({ value: '/repo' }))`). The test must answer `classic.Stop` itself (`() => ({})`). A test sees an ask indirectly: its own `classic.PreToolUse` hook is not reached and the tool still runs.
- Test inputs to a rule need `tool_use_id`.

## Style

Match the existing engines: small files, no mutation of inputs, comments only where the why is not obvious, no em-dashes in any text.
